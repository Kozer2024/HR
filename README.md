# HR BMSTU — управление рекламными размещениями

Веб-приложение для организаторов, администраторов и исполнителей: каталог рекламных точек, заявки, календарь занятости и контроль установки материалов.

## Технологии

- Next.js 16 (App Router), React 19 и TypeScript;
- Tailwind CSS 4;
- PostgreSQL 16 и Prisma 6;
- Auth.js Credentials, bcrypt и Zod;
- Docker Compose для локального PostgreSQL.

## Что нужно для локального запуска

- Windows 10/11, macOS или Linux;
- Node.js версии 20.9 или новее и npm;
- Docker Desktop (или Docker Engine с Compose);
- Git — только если вы клонируете проект или отправляете изменения на GitHub.

## Быстрый запуск на Windows (PowerShell)

Откройте PowerShell в папке проекта и выполните команды по порядку.

### 1. Создайте локальный файл конфигурации

```powershell
Copy-Item .env.example .env
```

Откройте `.env` в редакторе и задайте собственные `AUTH_SECRET`, `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Не оставляйте значения `REPLACE_...` и не отправляйте `.env` на GitHub. Для генерации секрета можно выполнить:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

Скопируйте выведенную строку в `AUTH_SECRET`. Для локальной разработки `AUTH_URL` должен быть `http://localhost:3001`. Строка `DATABASE_URL` в шаблоне соответствует локальному PostgreSQL из Compose.

### 2. Запустите PostgreSQL

```powershell
docker compose up -d
docker compose ps
```

Контейнер PostgreSQL должен перейти в состояние `healthy`. Данные БД сохраняются в Docker volume `pr_manager_postgres_data`; не удаляйте его, если хотите сохранить локальных пользователей и заявки.

### 3. Установите зависимости и подготовьте Prisma

```powershell
npm.cmd ci
npm.cmd run db:generate
npx.cmd prisma migrate deploy
```

`npm.cmd` используется в PowerShell, если политика запуска блокирует `npm.ps1`. `migrate deploy` применяет миграции, которые уже лежат в `prisma/migrations`; для обычного запуска не создавайте новую миграцию.

### 4. Создайте начального администратора и тестовую точку

После настройки `ADMIN_EMAIL` и `ADMIN_PASSWORD` в `.env`:

```powershell
npm.cmd run db:seed
```

Seed создаёт администратора с заданными вами реквизитами и одну демонстрационную точку. Не запускайте seed на рабочей базе повторно без понимания его поведения: запись пользователя с таким email будет обновлена и получит пароль из текущего env.

### 5. Запустите сайт

```powershell
npm.cmd run dev
```

Откройте [http://localhost:3001](http://localhost:3001). Для проверки основных публичных страниц, пока сервер работает, откройте второе окно PowerShell и выполните:

```powershell
npm.cmd run test:smoke
```

Остановка сервера — `Ctrl+C`. PostgreSQL можно оставить запущенным; остановить контейнеры без удаления данных можно командой `docker compose stop`.

| Команда | Назначение |

| `npm.cmd run test:smoke` | простая проверка `/`, `/login` и `/register` при работающем сервере |

## Разделы и роли

- **Организатор:** создание и просмотр запросов, календарь, установки и ссылки исполнителям.
- **Администратор:** запросы, пользователи, точки и корпуса, импорт, слоты экранов, ссылки исполнителям и журнал действий.
- **Исполнитель:** список назначенных установок по защищённой ссылке и отметка выполнения.

После регистрации организатор ожидает подтверждения администратора. Права проверяются на сервере; не считайте скрытие пункта меню единственной защитой.

## Файлы, фото и резервное копирование

Загруженные изображения хранятся в `FILE_STORAGE_PATH` (локально по умолчанию — папка `storage`). Папка намеренно исключена из Git: в ней могут быть пользовательские или внутренние фотографии. База PostgreSQL и файлы фотографий — разные данные, поэтому для восстановления сайта нужны резервные копии обоих.

Скрипт `scripts/backup-db.ps1` сохраняет резервную копию БД в `backups/`. Эта папка также исключена из Git. Настройте отдельное защищённое хранение копий `storage` и резервных копий базы; не публикуйте их в открытом репозитории.

## Безопасность и публикация

- Никогда не коммитьте `.env`, `.env.local`, пароли, токены Telegram, резервные копии БД, пользовательские фотографии или реальные ссылки доступа.
- Для общедоступного репозитория проверьте лицензию, права на изображения/логотипы и отсутствие персональных данных в исходниках и миграциях. Если есть сомнения — сделайте репозиторий **Private**.
- `.env.example` — только шаблон; seed намеренно откажется работать с его демонстрационными placeholder-значениями.
- `docker-compose.yml` предназначен для локальной разработки, а не для публикации PostgreSQL в интернет.
- Публикация кода на GitHub сама по себе не публикует работающий сайт и не переносит базу или фотографии.
- Для production понадобятся хостинг Node.js, PostgreSQL, постоянное файловое хранилище и production-переменные окружения. Настройте домен и HTTPS, затем выполните `npx prisma migrate deploy`. Не запускайте демо-seed на production.

## Загрузка проекта в новый GitHub-репозиторий

Следуйте шагам именно в этом порядке. Здесь подразумевается новый пустой репозиторий GitHub. Для сайта с рабочими данными безопаснее выбрать **Private**.

### Шаг 1. Установите Git и войдите в GitHub

Если Git ещё не установлен, скачайте Git for Windows с официального сайта `git-scm.com`, установите настройки по умолчанию и заново откройте PowerShell. Создайте аккаунт на GitHub, если его ещё нет, и войдите в него в браузере.

### Шаг 2. Создайте пустой репозиторий на GitHub

На GitHub нажмите **+ → New repository**. Укажите имя, например `hr-bmstu`, выберите видимость (рекомендуется **Private**) и нажмите **Create repository**. Не включайте опции создания README, `.gitignore` или License: локальный проект уже содержит эти файлы, и первый push будет проще с пустым удалённым репозиторием.

Оставьте страницу нового репозитория открытой: GitHub покажет адрес репозитория вида `https://github.com/ВАШ_ЛОГИН/hr-bmstu.git`.

### Шаг 3. Откройте PowerShell в папке проекта

Подставьте настоящий путь к папке, в которой находятся `package.json` и `prisma`:

```powershell
Set-Location "C:\путь\к\папке\проекта"
```

Проверьте, что это нужный проект:

```powershell
Get-ChildItem package.json, prisma\schema.prisma
git status --short --branch
```

### Шаг 4. Проверьте, что личные данные исключены

Убедитесь, что Git игнорирует локальные конфиги и фото, но **не** игнорирует шаблон `.env.example`:

```powershell
git check-ignore .env .env.local storage\example.jpg
git check-ignore .env.example
```

Первая команда должна вывести пути `.env`, `.env.local` и файла из `storage` (если такой тестовый файл существует). Вторая команда должна завершиться без вывода и с кодом 1 — это значит, что шаблон env можно включить в коммит. Не создавайте тестовую фотографию в реальной `storage` только ради этой проверки.

### Шаг 5. Запустите проверки и подготовьте первый коммит

```powershell
npm.cmd run lint
npm.cmd run build
git add -A
git status --short
git diff --cached --stat
```

Перед коммитом просмотрите список staged-файлов и убедитесь, что там **нет** `.env`, `.env.local`, `storage/`, `backups/`, `AI_HANDOFF.md`, дампов SQL и фотографий. Убедитесь также, что `.env.example`, `README.md`, `prisma/migrations/` и исходный код присутствуют.

Если личный файл случайно оказался в staged-изменениях, уберите его только из индекса (файл на компьютере останется):

```powershell
git restore --staged -- .env
```

Замените `.env` в команде на точное имя ошибочно добавленного файла. Если файл уже был в прошлых коммитах, одного `.gitignore` недостаточно — секрет нужно отозвать/сменить и отдельно очистить историю репозитория до публикации.

### Шаг 6. Укажите автора коммитов, если Git попросит

Используйте имя и email, которые хотите видеть в истории коммитов. Эти настройки можно сделать только для этого проекта:

```powershell
git config user.name "Ваше имя"
git config user.email "адрес, указанный в GitHub"
```

Если хотите, чтобы настройки действовали для всех ваших локальных репозиториев, добавьте параметр `--global`. Не указывайте чужой email.

### Шаг 7. Создайте первый коммит и подключите GitHub

```powershell
git branch -M main
git commit -m "Prepare HR BMSTU site for GitHub"
git remote add origin https://github.com/ВАШ_ЛОГИН/hr-bmstu.git
git remote -v
```

Замените `ВАШ_ЛОГИН` и `hr-bmstu` на точные значения со страницы своего репозитория. Команда `git remote -v` должна показать GitHub-адрес для fetch и push.

Если Git ответит `remote origin already exists`, не добавляйте второй origin вслепую. Сначала посмотрите текущий адрес через `git remote -v`; если он неправильный, замените его командой `git remote set-url origin https://github.com/ВАШ_ЛОГИН/hr-bmstu.git`.

### Шаг 8. Отправьте код на GitHub

```powershell
git push -u origin main
```

При HTTPS GitHub может открыть окно авторизации в браузере или запросить подтверждение. Обычный пароль аккаунта GitHub для Git push не используется. Пройдите авторизацию Git Credential Manager в появившемся окне; не вставляйте токены в команды и не сохраняйте их в файлах проекта.

Когда push завершится, обновите страницу GitHub: должны появиться файлы, README и папка `prisma/migrations`. В `.gitignore` скрытые секреты не отображаются в списке файлов — это ожидаемо. Если GitHub показывает секрет или загруженные фото, не продолжайте публикацию: удалите репозиторий/коммит или очистите историю и смените опубликованные секреты.

### Как отправлять следующие изменения

После редактирования проекта откройте PowerShell в его папке и выполните:

```powershell
git status
git add -A
git diff --cached --stat
git commit -m "Кратко опишите изменение"
git push
```

Каждый раз проверяйте staged-файлы перед коммитом. GitHub хранит историю исходного кода, но не заменяет резервную копию PostgreSQL и фотографий.
